Section 1 Project Overview

AI Upscaler is a local, browser-based image super-resolution tool that runs entirely on the user's own hardware. It exposes a FastAPI web server that serves both the UI and inference endpoints, making it accessible from any browser on the local network without requiring any cloud account or API key.

The application supports two primary workflows — single image upscaling with a before/after comparison slider, and batch folder processing with live per-image preview. Both workflows stream real-time tile-level progress to the browser via Server-Sent Events.

Core Goals

  • Zero-cloud: all inference runs locally
  • Best-in-class quality via Real-HAT
  • Low VRAM footprint via tiling + BF16
  • Real-time progress feedback
  • Simple drag-and-drop UX

Non-Goals

  • Cloud or SaaS deployment
  • Real-time video upscaling
  • Training or fine-tuning models
  • Face restoration (GFPGAN)
  • Mobile or tablet support

Section 2 System Architecture

The application follows a monolithic single-process design — the FastAPI server, model inference, and HTML delivery all run within the same Python process. This simplifies deployment (one command to start) while still achieving concurrency through Python threads for inference and asyncio for HTTP.

Concurrency Model

FastAPI runs on asyncio. Inference runs in a daemon thread so the event loop stays unblocked. Progress polling uses time.sleep(0.25) in the inference thread, not asyncio.

State Management

All task state lives in _tasks, a plain Python dict keyed by UUID. SSE generators read from this dict every 200ms. No database or message queue required.

Model Caching

Loaded models are stored in MODEL_CACHE and reused across requests. Loading HAT takes ~3–5s; subsequent requests start instantly.

Section 5 Tiling Strategy & Memory Management

Large images cannot be processed in one pass — a 2048×2048 image through HAT would require ~25 GB of VRAM for intermediate activations. Tiling splits the image into overlapping patches, processes each on the GPU, then stitches the results back seamlessly.

Overlap & Padding

Each tile is expanded by tile_pad=32 pixels on all sides before inference. After inference, only the non-padded center region is placed into the output canvas. This eliminates visible seams at tile boundaries caused by edge artifacts in convolutional/attention layers.

Tile = 256 px

~200 MB VRAM per tile. Best for 6 GB GPUs or when running multiple apps simultaneously.

Tile = 512 px (default)

~800 MB for HAT. Recommended for 8 GB GPUs — good balance of speed and safety.

Tile = 1024 px

~3 GB for HAT. Only suitable for 12+ GB GPUs. Faster due to fewer tile overheads.

CUDA Memory Management

PyTorch's CUDA allocator retains freed tensors in a pool for reuse. Without explicit release, this pool grows across tiles and can exhaust physical VRAM mid-batch. Two mitigations are applied:

torch.cuda.empty_cache()   # before inference — clear any stale pool
# ... inference ...
del tile_in                # free input tensor reference
torch.cuda.empty_cache()   # after each tile — prevent pool accumulation

Section 6 Numerical Precision Strategy

Choosing the wrong floating-point format for inference causes silent numerical failures. This section documents the precision decisions, the bugs they solve, and the hardware requirements.

Why HAT Overflows in FP16

HAT's Window Attention layer computes attention scores as Q × Kᵀ / √d. With d=30 (head dimension), scores can reach values of ±300 before softmax. In FP16, exp(300) overflows to inf, and inf / sum(inf) produces NaN. NaN propagates through the entire remaining forward pass, producing a black output image.

The symptom: Output PNG is 84 KB (solid black). numpy's astype(np.uint8) silently converts NaN to 0, so the error isn't raised — it just produces black pixels.

BF16 solves this by keeping the full 8-bit exponent of FP32 (same dynamic range, max ~3.4×10³⁸), while reducing the mantissa from 23 to 7 bits. The lower mantissa precision is acceptable for inference — the quality difference is imperceptible.

FP16 on HAT

Attention score overflow → NaN → black output. Unusable for HAT.

BF16 on HAT (Ampere+)

Full FP32 exponent range, no overflow. RTX 3000/4000 series support BF16 natively.

FP32 on HAT (fallback)

Correct numerics but 2× VRAM and ~3.4 GB per 512-tile → OOM on 8 GB GPU.

Section 8 UI / UX Design

Design Principles

  • Zero install UX — auto-opens browser on startup
  • Progressive disclosure — batch tab hidden until needed
  • Live feedback — every tile update streams instantly via SSE
  • No dead time — skeletons + spinners fill every wait state
  • Comparison slider — drag-based, no button clicks needed

Technology Choices

  • No JS framework — plain ES2020, zero build step
  • No Tailwind CDN — self-contained CSS variables
  • SSE over WebSocket — simpler, one-directional, HTTP/1.1 compatible
  • Inline HTML template — single file, no static file serving
  • CSS grid for tile viz — dynamic column count from JS
